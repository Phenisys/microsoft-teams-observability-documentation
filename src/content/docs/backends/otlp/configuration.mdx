## Collector Output Configuration

Add an `otel` entry under the `output` section of your `config.yaml`:

```yaml
output:
  otel:
    - name: "my-otel-backend"
      enabled: true
      endpoint: "https://your-otlp-endpoint/v1/logs"
      service_name: "ms-teams-agent"
      deployment_environment: "prod"
      headers:
        Authorization: "Bearer <token>"
```

### Parameters

| Parameter | Required | Description |
|---|---|---|
| `name` | Yes | Identifier for this OTLP output (used in logs) |
| `enabled` | Yes | Set to `true` to activate the OTLP output |
| `endpoint` | Yes | Full URL of the OTLP logs endpoint |
| `service_name` | No | Service name attached to exported logs |
| `deployment_environment` | No | Environment label attached to exported logs |
| `headers` | No | HTTP headers, usually used for authentication |

<Aside type="caution">
Keep OTLP credentials out of version control. Use secure secret management for API keys and tokens.
</Aside>

### Delivery behaviour

Each collector cycle is submitted to the backend in bounded batches, with a flush between
batches. The collector counts every record it submits: a cycle is reported as successful
only when every record has been delivered. When a batch fails, times out, or cannot be
confirmed, the remaining records are reported as failed, the export returns a failure, and
the collection state — deduplication marks and checkpoints — is not advanced, so the data
is collected again on the next cycle.

Consequence: delivery is **at-least-once**. After a partial failure, records already
accepted by the backend can be received twice.

<Aside type="note">
Two standard OpenTelemetry environment variables are honoured for this exporter:
`OTEL_BLRP_MAX_QUEUE_SIZE` and `OTEL_BLRP_MAX_EXPORT_BATCH_SIZE`. Lowering the batch size
increases the number of requests per cycle; it does not change the delivery guarantee.
</Aside>

## Datadog OTLP Configuration

```yaml
output:
  otel:
    - name: "datadog"
      enabled: true
      endpoint: "https://otlp.datadoghq.com/v1/logs"
      service_name: "ms-teams-agent"
      deployment_environment: "prod"
      headers:
        DD-API-KEY: "<api-key>"
```

Detailed setup: [OTLP to Datadog](../datadog/).

## Dynatrace OTLP Configuration

```yaml
output:
  otel:
    - name: "dynatrace"
      enabled: true
      endpoint: "https://{your-tenant}.live.dynatrace.com/api/v2/otlp/v1/logs"
      service_name: "ms-teams-agent"
      deployment_environment: "prod"
      headers:
        Authorization: "Api-token <token>"
```

<Aside type="note">
Dynatrace can be configured either with native `output.dynatrace` or via `output.otel` when your architecture is OTLP-first.
</Aside>

## Validate the Connection

After editing the configuration, run:

```bash
ms-teams-agent validate --config ./config.yaml
ms-teams-agent test-connection --config ./config.yaml
ms-teams-agent run --config ./config.yaml --dry-run
```

## Verify Data Arrival

1. Datadog: confirm logs arrive in Log Explorer and contain Teams event families.
2. Dynatrace OTLP: confirm logs arrive in Logs/Grail with expected source fields.
3. Generic OTLP receiver: confirm records are visible with the configured `service_name`.
4. If data is not arriving, check collector logs and then follow [Collector Troubleshooting](../../../collector/troubleshooting/).

✅ Success criteria:
- Collector logs confirm OTLP export with no errors
- Your OTLP platform shows logs from `service_name = "ms-teams-agent"`
- Event families (`MSTeams_CallRecords_*`) are visible in the platform

❌ If this fails:
- Re-run `validate` and `test-connection`
- Verify OTLP endpoint URL and authentication headers
